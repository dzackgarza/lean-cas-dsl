# Tasks: Categorical Mathematical Research Language

**Feature:** `001-categorical-research-language`. Read with the [specification](spec.md), the [plan](plan.md) and the [constitution](../../.specify/memory/constitution.md).

This file holds every task. "Part 1" names the sections from "Phase 0" to "Kernel readiness (F)". "Part 2" names the sections after "After kernel functionality". Task IDs are stable and are not renumbered. T008, T012, T024, T025 and T117 are retired. A checkbox changes only when the task meets its complete definition in the source.

## Execution order

The unchecked tasks are executed in the order of this document. The first unchecked task is the active task. Other work must serve the active task.

`After` names the inputs that a task needs for completion. It does not postpone the removal of a recovery path whose consumer has moved.

**An upstream dependency is a task (constitution C21).** When a task needs a mathematical declaration that lean-categories does not have, this file holds a task before it that supplies the declaration ([upstream tasks](#upstream-tasks)). Do it in lean-categories, then return to the consumer. An input that is found later gets its lean-categories issue and its task in the change that records it; no input waits for its consumer.

A wait on an environment that is not available blocks only the work that needs it (constitution C16). Complete the parts that do not need it and continue with the next unchecked task whose `After` inputs are present. The waiting task keeps its position and its checkbox.

**Kernel work and leaf work (constitution C22).** Every task of Part 1 is kernel work (owner K), except the upstream tasks (owner M) and the feedback tasks of Phase 0 (owner K/I). The checks of kernel work observe what the kernel does: the selected reading, the prepared request with its operation address and operands, the dispatch, the admission of the reply, the retained value and its later use, and the outcome when no leaf is registered. They use a protocol peer or an empty manifest. No Part 1 task, no checkpoint and not F requires a mathematically correct computed value. Such a value needs an implementation of every category on the selected structural route (for `2 * 3 = 6 in ℤ`: from sets up to rings). It belongs to the [computational milestones](plan.md#computational-milestones). A phase that is named for a user story completes the kernel work for the forms of that story; the story is accepted with computed results.

**Checkpoints (SC-014).** A [checkpoint of M1](plan.md#m1-checkpoints) is first observed in the closing of the task that its row names. The observation is part of that task. A checkpoint that does not hold then is observed again at the close of each later task until it holds.

A change of order is an edit of this file. The commit states the reason.

The [completion milestones](plan.md#completion-milestones) group outcomes on GitHub: #84 owns current feedback, [#92](https://github.com/dzackgarza/lean-cas-dsl/issues/92) owns complete F, and [#93](https://github.com/dzackgarza/lean-cas-dsl/issues/93) owns required category implementations and delivery. The broad owner issues keep every obligation through independent V1 acceptance and the later B0 and research phases ([issue-tree mapping](plan.md#issue-tree-and-task-order)). #86 is implemented at T307 inside #92; #90 is completed at T105 inside #93.

### Source-to-result rule

Preserve the original selected source judgment → form its whole typed mathematical application and source-derived dependencies once, including provider-requested computations at their own preparation boundary → bind actual computational occurrences without equality or endpoint searches → realize source functors through genuine public target-category constructors → execute and retain the complete selected result and its later use → delete the replaced recovery implementation. Keep the existing nonidentity RX-LIFT and factor cases and the unchanged-consumer cases as functional consumers; the opaque protocol peer is a transport and occurrence test, never mathematical acceptance. Repair a lost association where it was lost, not with a larger recognizer downstream. Do not improve expression matching, registry searches, name-based execution branches or independent runtime application builders.

### Upstream tasks

A task that names a lean-categories issue is done in lean-categories by this workstream as a formalization author (constitution, authorship rule; owner M): from the mathematics and its sources, at its own generality, not shaped to the request format of a consumer. It closes when the issue closes on its own acceptance and the lean-categories revision that the kernel pins contains the declarations. Its line names the missing input and its first consumer, which it precedes. The inputs of T118 to T138 were read at lean-categories `main` `443fba9` and at the published catalogue (mathematics revision `3f8aedf`); those of T225 to T234 at `f009120`.

Present upstream, and so no task: the comparison of the two multiplicative monoid routes of a ring (`cell.rings.multiplicative_monoid.semiring`, identity components, from the direct route to the route through semirings); equality as a published predicate (`mor.sets.equality`); an evidence procedure on each of the 15 admissions. A ring has three structural routes to monoids: direct, through semirings, and through its additive group. The three-valued reply of a decision is a shape of the reply in the contract and the kernel (T302); it needs no declaration of lean-categories.
